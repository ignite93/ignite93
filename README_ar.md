# ثمانية – مشروع خط أنابيب تفاعل لحظي  
(مشروع تجريبي في هندسة البيانات)

## نظرة عامة

هذا المشروع عبارة عن خط أنابيب بيانات (Data Pipeline) بسيط لكنه متكامل، مبني باستخدام الأدوات التالية:

- Kafka  
- Spark Structured Streaming  
- PostgreSQL  
- Docker  
- Python  

المشروع يهدف إلى محاكاة تفاعل المستخدمين مع المحتوى (مثل play / pause / finish / click)، ومعالجة هذه الأحداث في الوقت الحقيقي، ثم تخزينها في قاعدة بيانات، وبعدها استخراج تقارير تساعد على فهم سلوك المستخدمين.

الفكرة الأساسية:  
أوضح كيف أفكر في بناء نظام بيانات من البداية للنهاية:  
من توليد الأحداث → إلى المعالجة اللحظية → إلى التخزين → إلى التحليل والتقارير.

---

## لماذا نفذت هذا المشروع؟

هذا المشروع جزء من عملية تقييم تقنية، وحاولت أركز فيه على:

- أن يكون سهل التشغيل.  
- قريب من شغل هندسة البيانات في الواقع.  
- واضح في طريقة ربط المكوّنات ببعض.

خلال تنفيذ المشروع:

- طورت فهمي لـ Kafka و Spark Streaming بشكل عملي.  
- ربطت كامل السلسلة: استقبال البيانات → معالجتها → تخزينها → تحليلها.  
- اشتغلت على تتبّع الأخطاء (debugging) بين أكثر من خدمة (Kafka, Spark, Postgres, Docker).  
- حوّلت معلومات نظرية إلى تطبيق فعلي يشتغل من البداية للنهاية.

وبجانب هذا المشروع أنا حاليًا أتعلم وأطوّر نفسي في:

- تحليل البيانات (Data Analytics)  
- هندسة البيانات (Data Engineering)  
- Snowflake  
- تصميم حلول البيانات على السحابة (Cloud Data Architecture)

والانضمام لشركة سعودية مثل "ثمانية" بيكون شرف كبير لي، وواثق بقدرتي على التعلّم السريع وتقديم قيمة حقيقية للفريق.

---

## المعمارية (Architecture)

تدفق البيانات بشكل مبسّط:

**Event Producer → Kafka → Spark Structured Streaming → PostgreSQL → Analytics Reports**

- سكربت Python يولد أحداث تفاعل عشوائية.  
- الأحداث تروح إلى Kafka كـ stream.  
- Spark يقرأ الأحداث من Kafka ويجمعها في نوافذ زمنية (دقيقة).  
- PostgreSQL يخزن البيانات بشكل منظم.  
- سكربت `analytics_report.py` يطلع تقارير من قاعدة البيانات.

---

## المكوّنات الرئيسية

### Kafka

- استقبال الأحداث في الوقت الحقيقي.  
- استخدام topic واحد اسمه `engagement_stream`.

### Spark Structured Streaming

- قراءة الـ stream من Kafka.  
- فك JSON وتحويله إلى أعمدة (schema).  
- عمل تجميعات (Aggregations) في نافذة زمنية مدتها دقيقة، على مستوى:
  - وقت الحدث  
  - `content_id`  
  - `event_type`

### PostgreSQL

- تخزين البيانات في جداول مرتبة للتحليل.  
- الجداول الأساسية في المشروع:
  - جدول `content`  
  - جدول `engagement_events`

### Redis (اختياري)

- مضاف في `docker-compose.yml` كجزء من البيئة.  
- جاهز للاستخدام مستقبلاً كطبقة كاش (Caching Layer) لو حبينا نوسّع المشروع.

### Docker Compose

- مسؤول عن تشغيل كل الخدمات بأمر واحد:
  - Kafka  
  - Zookeeper  
  - PostgreSQL  
  - Redis  

### Python

كل السكربتات مكتوبة بـ Python:

- `Event_processing/events_producer.py`  
  - يولّد أحداث تفاعل ويرسلها إلى Kafka.  

- `Event_processing/events_stream_job.py`  
  - يشغل Spark Streaming، يقرأ من Kafka، ويطلع تجميعات في الزمن الحقيقي.  

- `Event_processing/analytics_report.py`  
  - يتصل بقاعدة بيانات PostgreSQL ويطبع تقارير جاهزة في الـ console.

---

## المزايا (Features)

- Streaming لحظي لأحداث التفاعل إلى Kafka.  
- تحويل الـ JSON إلى schema واضح داخل Spark.  
- تجميعات في نافذة زمنية مدتها دقيقة حسب الوقت و `content_id` و `event_type`.  
- تخزين مرتب في PostgreSQL، جاهز لأي استعلامات تحليلية.  
- سكربت تقارير بسيط يطلع أرقام مفيدة بشكل مقروء.  
- تصميم المشروع يسمح بالتوسعة بسهولة (إضافة تقارير أو جداول أو مصادر جديدة).

---

لتشغيل المشروع تحتاج:

- Python 3.10 أو أعلى  
- Docker Desktop  
- Docker Compose  
- JDK 17 (يفضّل Temurin)  
- PySpark 3.4.1 مع تكامل Kafka  
  - مضافة عن طريق `spark.jars.packages` داخل ملف `events_stream_job.py`

## طريقة التشغيل (How to Run)

> ملاحظة: الأوامر التالية مبنية على المسار اللي استخدمته في جهازي.  
> تقدر تعدّل المسار حسب مكان المشروع عندك.

### 1) الدخول على مجلد المشروع وتفعيل الـ virtualenv

في PowerShell:

    cd "C:\Users\user\Desktop\Abdulaziz Alkhateeb - thmanyah project"
    .\.venv\Scripts\Activate.ps1

### 2) تشغيل الخدمات (Kafka, Postgres, Redis, Zookeeper)

من نفس المجلد:

    docker compose up -d

هذا الأمر يشغّل:

- حاوية `thmanyah_kafka`  
- حاوية `thmanyah_zookeeper`  
- حاوية `thmanyah_postgres`  
- حاوية `thmanyah_redis`  

---

### 3) تشغيل سكربت إرسال الأحداث إلى Kafka

السكربت هذا يولّد أحداث تفاعل عشوائية ويرسلها إلى التوبك `engagement_stream`:

    python Event_processing/events_producer.py

المفروض تشوف في الـ PowerShell أسطر مثل:

    Sent: {"event_id": "...", "content_id": "...", "user_id": "...", ...}

تقدر توقفه يدويًا بـ `Ctrl + C` لما تكتفي من البيانات.

---

### 4) تشغيل Spark Streaming Job

السكربت هذا يقرأ الأحداث من Kafka، يفك JSON، ويسوي تجميعات في نافذة زمنية 1 دقيقة حسب `content_id` و `event_type`:

    python Event_processing/events_stream_job.py

النتائج تطلع في الـ console بشكل دفعات (batches)، مثال:

    -------------------------------------------
    Batch: 2
    -------------------------------------------
    +------------------------------------------+------------------------------------+----------+-----+
    |window                                    |content_id                          |event_type|count|
    +------------------------------------------+------------------------------------+----------+-----+
    |{2025-12-03 00:56:00, 2025-12-03 00:57:00}|8740f0a2-a248-4538-822f-76c1ddc7af38|pause     |1    |
    ...

---

### 5) تشغيل سكربت التقارير (Analytics)

السكربت هذا يتصل بقاعدة بيانات PostgreSQL ويطبع أكثر من إحصائية جاهزة:

    python Event_processing/analytics_report.py

أمثلة على الأشياء اللي يطبعها:

- إجمالي عدد الأحداث لكل `event_type`.  
- أكثر `content_id` عليه تفاعل.  
- نسبة الإكمال (عدد `finish` بالنسبة لعدد `play` لكل محتوى).  
- توزيع الأحداث على الأجهزة (ios / android / chrome / web-safari).

---

## أمثلة على الأسئلة اللي نقدر نجاوب عليها

من خلال هذا الـ pipeline نقدر نطلع إجابات على أسئلة مثل:

- ما هو المحتوى الأكثر تفاعلًا؟  
- ما نسبة المستخدمين اللي يكمّلون الاستماع/المشاهدة لمحتوى معيّن؟  
- أي جهاز عليه تفاعل أكبر (ios أو android أو المتصفح)؟  
- كيف يتوزّع التفاعل خلال آخر نصف ساعة مثلًا؟  
- ما هي أنواع الأحداث الأكثر حدوثًا (play / pause / click / finish)؟

وإذا توسّعنا لاحقًا نقدر نضيف:

- تحليل حسب `user_id`.  
- تحليل حسب نوع المحتوى (podcast / newsletter / video).  
- تحليلات أعمق مثل الـ retention أو سلوك الجلسة الواحدة (session).

## افتراضات (Assumptions)

- كل البيانات في هذا المشروع تجريبية (test data) ومولّدة عشوائيًا. الهدف هو توضيح فكرة الـ pipeline وليس تمثيل بيانات حقيقية من الإنتاج.  
- ما فيه طبقة أمن متقدّمة أو صلاحيات مستخدمين، لأن التركيز هنا على تدفّق البيانات ومعالجتها.  
- PostgreSQL هو مخزن البيانات الأساسي للتحليل.  
- Spark يكتب النتائج على الـ console لتسهيل التقييم بدل إعداد مخازن إضافية.  
- تشغيل السكربتات يتم يدويًا (ما استخدمت أدوات جدولة مثل Airflow) حتى يبقى المشروع بسيط وواضح.

## تحسينات مستقبلية ممكنة

- بناء API بسيط فوق طبقة التحليل لتغذية Dashboard أو خدمات أخرى.
